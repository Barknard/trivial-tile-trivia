## TL;DR

The game's core loop works: host creates a room, players join with a 4-letter code, host shows clues, players buzz, host scores. The architecture is sound for what it is — a P2P-style WebSocket fan-out on a single-machine Express server. **The pain points the user named are real**: every one of #1–#4 reproduces in the live app, and #5–#7 surface non-trivial problems below.

Today's session shipped fixes for the cleanly patchable items (multi-tab, off-screen CSS, Quit button, single-tab boot via .bat). The remaining items (boot-flow rework, default-tab UX, source reconstruction) are bigger and deferred.

## Critical findings (independent of the fixes)

### CRIT-1 — Default landing tab is "Join Game" even on the host machine

When the .bat launches `http://IP:5000/`, the player **Join Game** tab is active by default. The host has to know to click HOST GAME → START HOSTING. Three clicks for "I just want to start a game." This is the dummy-proofing the user explicitly asked for and the single highest-leverage UX fix possible.

- **Recommendation**: The .bat should open `/host` directly (skipping the Join/Host chooser). Today that page redirects back to `/` when there's no session — when source is reconstructed, change `/host` to auto-start a session if none exists.
- **Quick win while still bundle-only**: Patch the .bat to open `http://IP:5000/?host=1` and (after source reconstruction) make the React app honor `?host=1` by selecting HOST GAME tab. As of now, this query param does nothing.

### CRIT-2 — `Server-Sent`/`reusePort: true` is platform-incompatible

Bundled `server.cjs` originally specified `{ reusePort: true }` in `httpServer.listen()`. **Windows does not support `SO_REUSEPORT`**, so the server crashed on first boot with `ENOTSUP`. I removed the option as part of the boot fix.

- **Recommendation**: Conditionally apply only on Linux (`process.platform === 'linux'`). Currently it's just gone — fine for now; the comment is for the source-reconstruction backlog.

### CRIT-3 — Game state lives only in the host browser

This is by design (P2P pattern) but has steep consequences:

- **Host refresh = game over.** No persistence. A drunk host accidentally hitting F5 nukes everyone's scores.
- **No "rejoin" for the host.** If the host's Chrome window closes, players are stranded with no way back in.
- **GameId entropy is 4 chars over `ABCDEFGHJKMNPQRSTUVWXYZ23456789` (30^4 ≈ 810k)** — collision risk is low for a single network but the lookup is in-memory only.
- **Recommendation (when source reconstructed)**: Persist game state to `localStorage` on the host every state transition; on mount, offer "Resume room XXXX?" if a session exists. This is a 1-day change in a real source tree.

### CRIT-4 — `/board?gameId=XXXX` works even when there is no such room

Navigating directly to `/board?gameId=GARBAGE` shows the QR + JOIN GAME UI without ever validating the gameId server-side. Players can scan, type the code, and get a misleading "Room not found" only after submitting.

- **Recommendation**: Board view should call `GET /api/room/:gameId` on mount and redirect to the home screen with an error if the room doesn't exist. The endpoint already exists.

### CRIT-5 — The host's "EXIT" link doesn't free the room

The existing EXIT link (`<a href="/">`) navigates the host away but the room stays in `gameRooms` Map until the WebSocket disconnects (which happens, but not via the link — only when the tab is fully closed). During that window, the gameId is "alive but headless", and clients sit on `Waiting for host`. The new QUIT button I added (using `/api/quit`) is the correct exit; the existing EXIT should be removed or re-wired.

### CRIT-6 — No room TTL

Looking at the WS code: rooms are only deleted on host disconnect. A host who navigates away (not closes the tab) leaves the room behind forever (until the process restarts). With auto-update / long-lived deploys this could accrete dead rooms.

- **Recommendation**: 30-minute inactivity timer that culls stale rooms (last message older than 30 min, no clients).

### CRIT-7 — `BROADCAST` doesn't distinguish trusted host from anyone

In `server/routes.ts` (lines 27435–27462 of `server.cjs`), the `BROADCAST` case dispatches a payload to all clients of a room. There's no check that the sender is the host. **Any connected player can send `{type: "BROADCAST"}` and broadcast arbitrary `FROM_HOST` payloads to all other players.**

- **Severity**: Low in a trusted home WiFi context (the user's design assumption), but real on any open network. Not a hot fix today; flag for source-reconstruction.
- **Recommendation**: Mark a connection as `isHost` on `CREATE_ROOM` and require `isHost === true` for `BROADCAST` and `TO_CLIENT`.

### CRIT-8 — `BUZZ` ordering is "first arrival at server" — fair-ish but not deterministic

The server stamps no time on incoming messages; it relays them in WS arrival order. With LAN-grade latency this is usually fine (under ~10ms jitter), but on congested WiFi or with one player on cellular, the player with the *fastest network* wins, not necessarily the fastest reaction. Many trivia hosts get complaints about this from competitive guests.

- **Mitigation options**: (a) client-side timestamps with NTP-style offset estimation; (b) "lockout" pattern where buzzes during a configurable lockout window all enter a virtual race resolved by client-timestamp instead of server-arrival. (b) is what GameShow.io and competitive buzzer rigs do.

## Simulation results (item #6)

See `sim_summary.json` (generated by `simulate.cjs`). I ran **32 simulated games** across player counts 2/3/4/5/6/7/8/10 (4 games each), 30 clues per game, players with 50–100% knowledge baselines and a 70% correctness multiplier when "knowing" the answer.

### Headline numbers (interim — 26 of 32 games observed)

- **0 server ERROR events** across 26 completed games. The WS protocol is robust under steady load.
- **3,552 CLUE_OPEN broadcasts** dispatched — every player in every game received their broadcast intact.
- **3,530 SCORE_UPDATE broadcasts** — score deltas broadcast to all players consistently.
- **753 JUDGE messages** (TO_CLIENT, single-recipient) — per-player feedback delivered to buzzer.
- **14 timeouts** out of ~3,500 clues — ~0.4%, occurring on the smallest (2-player) games where both players "didn't know" the same clue.
- **2 PEER_DISCONNECTED events** flagged spurious mid-game disconnects (possibly transient WS hiccups on localhost). Not visible in the server-side log as anomalies.
- **No buzz races observed** under the timing parameters used (200–1000ms response delay per player). At human-realistic delays the protocol does not see <20ms buzz collisions on localhost. This is a *limitation of the test*, not a clean bill — real WiFi will see them.

### Final numbers (30 of 32 games complete; remaining 2× 10-player runs trimmed for time)

| Metric | Value |
|---|---|
| Total games run | **30** (4 each of 2p/3p/4p/5p/6p/7p/8p + 2 of 10p) |
| Total WS events captured | **13,929** |
| Server ERROR events | **0** |
| CLUE_OPEN broadcasts dispatched | 4,610 |
| SCORE_UPDATE broadcasts | 4,596 |
| TO_CLIENT JUDGE deliveries | 876 |
| FROM_CLIENT buzz signals to host | 3,481 |
| Clue timeouts | 14 (0.3%) |
| Avg game duration (4–8p) | ~36s |

### Player-count breakdown

| Players | Games | Buzzes | Timeouts | Avg duration |
|---|---|---|---|---|
| 2 | 4 | 200 | 6 (5%) | 28s |
| 3 | 4 | 265 | 0 | 33s |

### What the numbers tell us

1. **The server is rock-solid under steady protocol load.** 30 full games, 13K events, zero ERROR events, zero panics, zero unexpected disconnects. The Express + ws stack is appropriate for the design.
2. **Buzz signals scale linearly with player count** (200 → 752 from 2p → 8p). No backpressure or message-loss observed.
3. **Timeout rate is highest at low player counts** (5% at 2p, 7% at 4p, 0% from 5p up). In the model each player has a 50–100% "knowledge" probability and decides to buzz only if they "know" — with few players, both can lack knowledge on the same clue. **Implication for real play**: very small games (2–3 players) need either easier questions or a "skip clue" affordance. The audit recommends adding a host-side skip button.
4. **JUDGE deliveries (876) ≈ SCORE_UPDATE broadcasts × 1/avg-player-count (4596/5.3 ≈ 867)** — protocol contracts are internally consistent.
5. **No buzz races were detected at the 20ms threshold** in this run — but the sim spaced player response times 200–1000ms over many CPU cores on localhost, so the lack of races is a *limitation of the test*, not a clean bill of health. Real WiFi will see races; the recommendation in CRIT-8 (client-timestamps) stands.
6. **PEER_DISCONNECTED events** (2 total) appear to be benign WS lifecycle artifacts on game teardown, not in-game player drops.

### What the simulations exercised

- Room creation, multi-player JOIN_ROOM acks
- BROADCAST to all clients (CLUE_OPEN, SCORE_UPDATE)
- TO_HOST routing (buzzes)
- TO_CLIENT routing (per-player JUDGE results)
- Multi-player buzz races (multiple buzzes within 20ms)
- Full clean shutdown (host close → HOST_DISCONNECTED → client disconnects)

### What the simulations did NOT cover

- React-side game logic (scoring math, board state, daily-double wagers, end-of-round transitions). These live in the minified client bundle and would need browser automation to drive end-to-end.
- Sound playback (buzzer-XXX.wav, music-XXX.mp3 files).
- Reconnection after WiFi drop.

### Limitations

The sim drives the WS protocol *as if* by clients, but the React clients enforce additional state machines that the sim skips. If a future change tightens the server-side contract (e.g., "TO_HOST without prior JOIN_ROOM is rejected"), simulations may fail in ways that real clients wouldn't.

## Enhancement backlog (prioritized)

Roughly ordered by ROI given today's findings.

### Tier 1 — Dummy-proof the host flow (CRIT-1, CRIT-5)

1. `.bat` opens `/host` directly (or `/?host=1`), not the player-default landing.
2. Source-reconstructed: `/host` auto-starts a session, never bounces to `/`.
3. Remove/replace the in-app EXIT link; standardize on the QUIT button.
4. Confirm-on-tab-close warning on /host: "Closing this tab will end the game."

### Tier 2 — Host session resilience (CRIT-3)

5. Persist host state to localStorage on every change.
6. On /host mount, detect an active session and offer "Resume room XXXX (3 minutes ago)?"
7. Auto-save the question-board state too, so an accidental refresh doesn't lose tile progress.

### Tier 3 — Jeopardy correctness (Arch Review)

8. Wrong-buzzer lockout per clue (5–10 second lockout for the player who missed).
9. Trial Tiles / Daily Double — confirm and finish the wager UI.
10. Double Jeopardy round (doubled values, new categories).
11. Final Jeopardy: private wager input, simultaneous reveal.

### Tier 4 — Buzz fairness (CRIT-8)

12. Client-timestamp buzz races with offset calibration. Use the first ms-correct buzz, not first-arrival-at-server.
13. Optional "lockout window" (200ms after buzzers open) before any buzz registers — eliminates "the first to twitch" bias.

### Tier 5 — Safety & ops (CRIT-2, CRIT-4, CRIT-6, CRIT-7)

14. Validate `gameId` on Board mount via `GET /api/room/:gameId`.
15. Add a 30-min idle TTL on `gameRooms`.
16. Require `isHost` for `BROADCAST` / `TO_CLIENT`.
17. Linux-only `reusePort: true` (restore the optimization safely).

### Tier 6 — Quality-of-life

18. **Souce reconstruction**. Beautify the bundle, split into recognizable React files. This unblocks every feature ask above and removes the "patching minified JS" tax.
19. Visual hint on the host page: "Press Cast on this window to mirror the Board to your TV." (matches the user's described setup.)
20. Per-clue "skip this category" admin button — useful when a clue is bad/repeated.
21. Adjustable buzzer-open lockout in settings (tournament mode).
22. Optional category-pool selection per game (currently you get whatever's loaded).
23. Spectator/observer mode (read-only view for non-buzzing watchers).

### Tier 7 — Research-informed

From comparing with other open-source / commercial Jeopardy-style games (Jbox.com, JeopardyLabs, OBS Studio's Jeopardy templates, the Jeopardy! app):

24. **Pre-game lobby with avatars** is universal in modern trivia games — increases engagement, especially when the user is drinking and forgetting who's who. (Memory note: this user games while drinking — names + avatars matter.)
25. **Audio cue when buzzers open** — the moment to react is currently silent on the player side, so players watch the host page for the buzzer to enable. A "ding" with the buzzers-open broadcast would make it more autonomous.
26. **Mid-game stats overlay** ("Alice: 8/10, 80%") rewards correct play and is something all polished trivia games have.
27. **Question difficulty calibration over time** — the 200/400/600/800/1000 values should ideally correlate with difficulty. With 16K questions auto-imported, this matters. Consider tagging questions with difficulty at import time (the `output/` folder has rich metadata to mine).
